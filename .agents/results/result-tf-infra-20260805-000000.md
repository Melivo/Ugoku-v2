## Produktionsschritte

In einem Wartungsfenster und aus dem Repository-Stamm:

```sh
sudo install -o root -g root -m 0644 deploy/*.service deploy/*.timer /etc/systemd/system/
sudo visudo -cf deploy/ugoku-restart.sudoers
sudo install -o root -g root -m 0440 deploy/ugoku-restart.sudoers /etc/sudoers.d/ugoku-restart
sudo systemctl daemon-reload
sudo systemctl enable --now ugoku.service ugoku-health.timer
```

Bei einem bereits laufenden `ugoku.service` ist danach ein kontrollierter Restart nötig, damit die neue Unit wirksam wird. Zuvor sicherstellen, dass der HealthMonitor `READY=1` und alle 20 Sekunden `WATCHDOG=1` sendet. Anschließend prüfen:

```sh
sudo systemctl restart ugoku.service
systemctl status ugoku.service ugoku-health.timer
systemctl list-timers ugoku-health.timer
systemctl show ugoku.service -p Type -p WatchdogUSec -p RuntimeDirectoryPreserve
sudo -l -U leadt3ch
journalctl -u ugoku.service -u ugoku-health.service -u ugoku-alert-onfailure.service --since "10 minutes ago"
```

`ugoku-alert-onfailure.service` nicht separat aktivieren; `OnFailure=` startet sie implizit.

## Betrieb, Drift, Kosten und Rollback

- **Kosten:** keine neue Cloud-Ressource; nur geringe lokale CPU-/I/O-Last durch einen Check alle 120 Sekunden sowie potenzieller Webhook-Traffic.
- **Drift:** `deploy/` bleibt Sollzustand. Root-Eigentümer/Modi der installierten Units und `/etc/sudoers.d/ugoku-restart` regelmäßig prüfen; Änderungen unter `/etc/systemd/system` nicht manuell vom Repository entkoppeln.
- **Kontinuität:** `RuntimeDirectoryPreserve=restart` erhält `incident.json` über Service-Restarts. `/run` bleibt jedoch flüchtig bei Reboot oder vollständigem Stop; Alerts hängen von Netzwerk und externem Discord-Webhook ab.
- **Rollback:** Timer stoppen/deaktivieren, vorherige `ugoku.service` wiederherstellen, die drei neuen Unit-Dateien und das sudoers-Snippet entfernen, `daemon-reload` ausführen und den Hauptdienst kontrolliert neu starten. Vor einem vollständigen Stop bei forensischem Bedarf `/run/ugoku/incident.json` sichern.
